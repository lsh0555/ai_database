# 2. 프로젝트 범위와 요구사항 읽기

## 2-1. 포함 범위

본문을 그대로 복사하지 말고 자신의 말로 정리합니다.

```text
1. 정규화 전 큰 테이블의 문제점을 찾고 삽입·수정·삭제 이상을 설명한다.
2. 1NF, 2NF, 3NF의 기준을 이용하여 데이터 구조를 분석한다.
3. 회원, 도서, 대여 정보를 적절한 테이블로 분리하고 무결성 제약조건을 적용한다.
4. 정상·경계·실패 데이터를 직접 실행하여 제약조건이 업무 규칙을 올바르게 보호하는지 검증한다.
```

## 2-2. 제외 범위

```text
1. 웹 화면이나 사용자 인터페이스(UI) 구현은 진행하지 않는다.
2. 로그인, 회원가입과 같은 인증 기능은 구현하지 않는다.
3. 실제 서비스 배포나 서버 운영은 진행하지 않는다.
4. 이번 프로젝트에서 요구하지 않는 추가 기능이나 복잡한 업무 기능은 구현하지 않는다.
```

### 범위를 명확하게 정해야 하는 이유

```text
범위가 명확하지 않으면 필요하지 않은 기능까지 구현하거나 반대로 반드시 구현해야 하는 요구사항을 놓칠 수 있다.
프로젝트 시작 전에 범위를 정하여 개발 기준을 명확하게 하고 불필요한 작업을 줄여야 한다.
```

# 3. 네 테이블의 한 행 의미와 관계

## 3-1. 한 행 의미

```text
course_project.students 한 행 = 학생 한 명의 정보를 의미한다.

course_project.instructors 한 행 = 강사 한 명의 정보를 의미한다.

course_project.courses 한 행 = 개설된 강의 한 개의 정보를 의미한다.

course_project.enrollments 한 행 = 특정 학생이 특정 강의를 수강하는 관계 한 건을 의미한다.
```

## 3-2. 키와 중요 규칙

| 테이블 | PK | FK | 중요 규칙 |
| --- | --- | --- | --- |
| students | id | 없음 | 학생 이메일은 테이블 내부에서 고유해야 하며 이름과 이메일은 빈 문자열일 수 없다. |
| instructors | id | 없음 | 강사 이메일은 테이블 내부에서 고유해야 하며 이름, 이메일, 전문 분야는 빈 문자열일 수 없다. |
| courses | id | instructor_id → instructors.id | 존재하는 강사와 연결되어야 하며 level은 basic, intermediate, advanced 중 하나이고 price는 0 이상이어야 한다. |
| enrollments | id | student_id → students.id, course_id → courses.id | 존재하는 학생과 강의만 연결하며 신청·수강중 상태에서는 동일 학생의 동일 강의 중복 신청을 허용하지 않는다. |

## 3-3. 관계를 양방향 문장으로 작성

```text
instructors ↔ courses : 한 명의 강사는 여러 강의를 담당할 수 있고, 각 강의는 한 명의 강사와 연결된다.

students ↔ enrollments : 한 명의 학생은 여러 수강 기록을 가질 수 있고, 각 수강 기록은 한 명의 학생과 연결된다.

courses ↔ enrollments : 하나의 강의는 여러 수강 기록을 가질 수 있고, 각 수강 기록은 하나의 강의와 연결된다.
```

### 학생과 강의의 N:M 관계가 `enrollments`를 통해 어떻게 바뀌는지 설명

```text
N:M 관계를 직접 연결 할 수 없기 때문에 enrollments 테이블을 중간에 두어 students와 enrollments의 관계와 courses와 enrollments의 관계를 각각 1:N 관계로 연결해줍니다.
```

### `enrollments`가 단순 연결 테이블이 아니라 사건 테이블이라고 볼 수 있는 이유

```text
enrollments는 단순히 학생과 강의를 연결하는 역할만 하는 것이 아니라 특정 학생이 특정 강의를 수강 신청한 하나의 사건을 기록하는 테이블이기 때문이다.
```

# 4. `recorded_amount`의 의미 이해

```text
courses.price = 현재 강의에 설정되어 있는 수강 가격

enrollments.recorded_amount = 학생이 수강 신청한 당시 기록된 금액
```

### 두 값이 처음에는 같아도 같은 의미가 아닌 이유

```text
수강 신청 시점에는 두 값이 같을 수 있지만 나중에 강의 가격이 변경되면 courses.price는 변경될 수 있는 반면
recorded_amount는 신청 당시의 금액을 그대로 보존하기 때문이다.
```

### `recorded_amount`를 실제 결제 성공액이나 회계 매출로 해석하면 안 되는 이유

```text
recorded_amount는 수강 신청 사건 당시의 금액을 기록한 값일 뿐 실제로 결제가 성공했다는 사실이나 회계상 매출이 발생했다는 것을 의미하지 않기 때문에 recorded_amount만으로 실제 결제 금액이나 회계 매출을 판단하면 안 된다.
```

```text
왜 허용되어야 하는가 : 강의 가격과 신청 당시 기록 금액은 0 이상으로 설정되어 있으므로 0은 정상적인 경계값이다. 또한 description은 NOT NULL 제약조건이 없기 때문에 NULL을 허용한다.
```

## 9-2. 실패해야 하는 테스트 1 — 잘못된 참조 또는 값

```text
테스트 내용 : 존재하지 않는 학생 ID 999를 참조하여 수강 신청을 추가한다.
기대 결과 : INSERT가 실패해야 한다.
실제 오류 핵심 : foreign key constraint 위반
동작한 제약조건/규칙 : fk_course_enrollments_student
왜 실패해야 하는가 : enrollments.student_id는 students.id를 참조하므로 존재하지 않는 학생 999를 수강 신청에 사용할 수 없기 때문이다.
```

## 9-3. 실패해야 하는 테스트 2 — 활성 중복 신청

```text
테스트 내용 : 학생 101이 강의 302에 두 번째 활성 신청(수강중)을 추가한다.
기대 결과 : INSERT가 실패해야 한다.
실제 오류 핵심 : duplicate key value violates unique constraint
동작한 인덱스/규칙 : uq_course_enrollments_active
왜 실패해야 하는가 : 학생 101은 이미 강의 302에 '신청' 상태의 활성 신청 1002가 있으므로 같은 학생과 같은 강의에 '신청' 또는 '수강중' 상태의 활성 신청을 중복으로 만들 수 없기 때문이다.
```

## 14-1. AI에게 전달한 핵심 자료

```text
요구사항 :
참여자와 스터디 정보를 저장하고, 참여자가 여러 스터디에 참여할 수 있도록 관리한다.

participants는 참여자 정보를 저장하고, studies는 스터디 정보를 저장한다.

한 참여자가 하나의 스터디에서 여러 역할을 동시에 가질 수 있도록 할 것인가?
```

```text
참여자와 스터디 정보를 저장하고, 참여자가 여러 스터디에 참여할 수 있도록 관리한다.
참여 관계별 가입일, 역할, 참여 상태를 기록하며 스터디별 여러 모임 일정도 관리한다.

테이블/ERD 설명 :
participants는 참여자 정보를 저장하고, studies는 스터디 정보를 저장한다.
participations는 participants와 studies의 N:M 관계를 연결하며 역할, 가입일, 참여 상태를 저장한다.
meetings는 각 스터디에서 진행되는 여러 모임 일정을 저장하며 studies와 1:N 관계를 가진다.

프로젝트 결정 :
참여자와 스터디의 N:M 관계를 participations 중간 테이블로 구현한다.
역할, 가입일, 참여 상태는 특정 스터디 참여 시 발생하는 정보이므로 participations에 저장한다.
반복되는 스터디 모임 일정은 meetings 테이블로 분리하여 관리한다.

미확정 질문 :
같은 참여자가 같은 스터디에 다시 참여할 수 있도록 허용할 것인가?
스터디에서 탈퇴한 참여자의 기존 참여 기록을 계속 보관할 것인가?
한 참여자가 하나의 스터디에서 여러 역할을 동시에 가질 수 있도록 할 것인가?

완료 기준 :
참여자와 스터디 정보를 각각 2건 이상 저장하고 조회할 수 있어야 한다.
한 참여자가 여러 스터디에 참여하고, 하나의 스터디에 여러 참여자를 등록할 수 있어야 한다.
참여 기록의 가입일, 역할, 참여 상태를 저장하고 조회할 수 있어야 한다.
하나의 스터디에 여러 모임 일정을 저장하고 조회할 수 있어야 한다.
```

## 14-3. AI 제안 검토

| AI 제안 | 수용 / 수정 / 보류 / 거절 | 실제 근거 | 반영 내용 |

| 요구사항에 있는 meetings 테이블을 ERD에도 반영해야 한다. | 수용 | 스터디별 모임 일정을 여러 번 기록해야 한다는 요구사항이 있음 | meetings 테이블과 studies 1:N 관계를 ERD에 반영한다. |
| participations의 중복 참여 방지 여부를 결정해야 한다. | 보류 | 같은 참여자의 동일 스터디 재참여 허용 여부가 아직 미확정임 | UNIQUE 등의 제약조건을 바로 추가하지 않고 정책 결정 후 반영한다. |

### AI가 미확정 정책을 임의로 확정하려 한 부분이 있었나요?

```text
같은 참여자가 같은 스터디에 다시 참여할 수 있는지 아직 결정하지 않았는데,
AI가 participant_id와 study_id에 UNIQUE 제약조건을 적용하는 방안을 제시할 수 있었다.
하지만 재참여 정책이 미확정이므로 해당 제약조건은 바로 적용하지 않고 보류했다.

또한 한 참여자가 하나의 스터디에서 여러 역할을 가질 수 있는지도 미확정이므로
role 구조 역시 현재 단계에서 임의로 확정하지 않았다.
```

### AI가 제안한 규칙 중 아직 배우지 않은 기능이라 보류한 것이 있나요?

```text
복합 UNIQUE, CHECK 제약조건, ON DELETE CASCADE 등의 기능을 적용하는 방안이 있었지만,
현재 프로젝트 요구사항에서 반드시 필요한 기능이 아니며 아직 충분히 배우지 않은 내용이므로 보류했다.

현재 단계에서는 기본적인 PK, FK와 1:N, N:M 관계를 정확하게 설계하고
Seed 데이터와 SELECT를 이용해 요구사항을 검증하는 것에 집중하기로 했다.
```

### AI 활용 후 실제로 좋아진 부분

```text
요구사항과 ERD를 다시 비교하면서 문서에는 있지만 기존 ERD에는 없었던
meetings 테이블이 누락되어 있다는 점을 확인할 수 있었다.

또한 participations의 role, joined_at, status가 참여자 자체의 정보가 아니라
특정 스터디에 참여하면서 발생하는 정보라는 점을 다시 확인했다.

미확정된 정책을 바로 DB 제약조건으로 구현하지 않고,
먼저 정책을 결정한 후 데이터베이스 설계에 반영해야 한다는 점도 명확해졌다.
```
