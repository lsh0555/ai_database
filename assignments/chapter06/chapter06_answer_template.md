# 2. 정규화 전 큰 테이블의 문제 찾기

본문의 `library_records_raw` 구조를 기준으로 생각합니다.

```text
library_records_raw 한 행
→ 대여 사건 한 건이지만 회원·도서의 현재 사실까지 함께 저장된 구조
```

## 2-1. 위험한 중복과 의미 있는 반복 구분

| 반복되는 값/상황 | 위험한 중복 / 의미 있는 반복 | 판단 이유 |
| --- | --- | --- |
| 회원 이메일이 여러 대여 행에 반복 | 위험한 중복 | 회원 이메일이라는 하나의 현재 사실이 여러 대여 기록에 복사되기 때문 |
| 도서 제목이 여러 대여 행에 반복 | 위험한 중복 | 도서 제목은 도서 자체의 정보인데 대여할 때마다 같은 값이 복사되기 때문 |
| `loans_nf.member_id = 101` 반복 | 의미 있는 반복 | 회원 101이 여러 번 대여했다는 서로 다른 대여 사건의 관계를 나타내기 때문 |
| 사건 당시 가격 같은 이력값 반복 | 의미 있는 반복(이력) | 각 사건이 발생했을 당시의 값을 보존하기 위한 기록이기 때문 |

## 2-2. 이상 현상 설명

### 삽입 이상

```text
아직 한 번도 대여되지 않은 새 도서를 등록하려 할 때 생기는 문제 : 대여 기록을 기준으로 도서 정보를 저장하는 구조이기 때문에 대여가 발생하지 않은 새 도서의 정보만 따로 등록하기 어렵다.
```

### 수정 이상

```text
회원 이메일이 변경될 때 생기는 문제 : 같은 회원의 이메일이 여러 대여 행에 반복되어 있으므로 해당 회원의 이메일이 들어 있는 모든 행을 중복이 없게 수정해야 한다. 일부 행만 수정하면 같은 회원인데 서로 다른 이메일이 저장되는 데이터 불일치가 발생할 수 있다.
```

### 삭제 이상

```text
마지막 대여 기록을 삭제할 때 생길 수 있는 문제 : 대여 기록과 도서 정보가 같은 행에 저장되어 있기 때문에 마지막 대여 기록을 삭제하면 대여 정보뿐만 아니라 도서 자체의 정보까지 함께 사라질 수 있다.
```

### 왜 이것이 SQL 문법 문제가 아니라 구조 문제인가요?

```text
SQL 문법 자체는 정상적으로 실행되지만 회원·도서·대여처럼 서로 다른 정보가 하나의 테이블에 함께 저장되어 있기 때문에 발생하는 문제이다. 그렇기 때문에 SQL 문법을 수정하는 것이 아니라 회원, 도서, 대여 정보를 각각 알맞은 테이블로 분리하여 데이터 구조를 개선해야 한다.
```

# 3. 1NF·2NF·3NF 핵심 질문 복습

정규형 이름만 외우지 말고 **왜 분리하는지** 설명합니다.

## 3-1. 제1정규형(1NF)

```text
한 셀에 쉼표로 여러 독립 값을 넣거나 book1/book2/book3처럼 반복 열을 만들면 왜 문제가 되는가 : 
한 셀에 여러 독립적인 값을 저장하면 각각의 값을 개별적으로 검색하거나 수정하기 어렵고, 다른 테이블과 외래키로 연결하기도 어렵다.

book1, book2, book3처럼 반복 열을 만들면 데이터가 늘어날 때마다 새로운 컬럼을 추가해야 하므로 테이블 구조를 계속 변경해야 하기 때문에 반복되는 독립적인 값은 한 셀이나 여러 컬럼에 넣지 않고 각각의 행이나 별도의 관계로 관리해야 한다.
```

내 서비스에서 비슷한 위험이 있는 예 : 

```text
LMS에서 한 과제에 제출한 학생들을 student1, student2, student3처럼 여러 컬럼으로 저장하는 경우가 있다.

이렇게 하면 제출 학생이 늘어날 때마다 새로운 컬럼을 추가해야 하고, 학생별 제출 정보를 검색하거나 수정하기 어려워진다.

따라서 학생의 과제 제출 정보는 별도의 제출 테이블에서 학생 한 명의 제출을 하나의 행으로 관리하는 것이 적절하다.
```

## 3-2. 제2정규형(2NF)

다음 관계를 설명합니다.

```text
(student_id, course_id) → grade
student_id → student_name
course_id → course_name
```

```text
복합키 전체가 아니라 일부에만 의존하는 열을 분리해야 하는 이유 : student_name은 student_id만으로 결정되고, course_name은 course_id만으로 결정되기 때문에
복합키 전체에 의존하지 않는 정보를 분리해야 중복과 수정 이상을 줄일 수 있다.
```

## 3-3. 제3정규형(3NF)

```text
member_id → zip_code
zip_code → city
```

```text
일반 열이 다른 일반 열을 결정하는 구조를 검토해야 하는 이유 : zip_code가 city를 결정하면 city는 member_id에 직접 의존하는 것이 아니라
zip_code를 거쳐 간접적으로 의존하게 된다.
따라서 이런 구조를 분리해야 같은 정보를 반복 저장하는 문제를 줄일 수 있다.
```

### 정규화는 값이 반복되기만 하면 무조건 분리하는 것인가요?

```text
정규화는 값이 반복된다는 이유만으로 무조건 분리하는 것이 아니다.
같은 사실을 여러 행에 중복 저장하여 삽입·수정·삭제 이상이 발생하는지를 확인하고,
각 데이터가 누구의 사실인지와 어떤 키에 의존하는지를 기준으로 분리해야 한다.
```

# 4. 각 열의 '사실의 주인' 찾기

| 열 | 어떤 사실을 설명하는가 | 주인 테이블 | 이유 |
| --- | --- | --- | --- |
| `member_name` | 회원의 이름 | `members_nf` | 회원 자체의 정보이기 때문이다. |
| `member_email` | 회원의 이메일 | `members_nf` | 회원 자체의 정보이기 때문이다. |
| `book_title` | 도서의 제목 | `books_nf` | 도서 자체의 정보이기 때문이다. |
| `author` | 도서의 저자 | `books_nf` | 도서 자체의 정보이기 때문이다. |
| `borrowed_at` | 도서를 빌린 날짜 | `loans_nf` | 대여 사건이 발생한 시점의 정보이기 때문이다. |
| `due_at` | 도서의 반납 예정일 | `loans_nf` | 해당 대여 사건에 대한 정보이기 때문이다. |
| `returned_at` | 실제 반납일 | `loans_nf` | 해당 대여 사건의 반납 상태를 나타내기 때문이다. |
| `member_id` | 어떤 회원이 대여했는지 | `loans_nf` | 대여 사건과 회원을 연결하기 위한 FK이기 때문이다. |
| `book_id` | 어떤 도서를 대여했는지 | `loans_nf` | 대여 사건과 도서를 연결하기 위한 FK이기 때문이다. |

정규화 후 한 행의 의미:

```text
members_nf 한 행 = 회원 한 명의 정보를 의미한다.
books_nf 한 행 = 도서 한 권의 정보를 의미한다.
loans_nf 한 행 = 특정 회원이 특정 도서를 대여한 한 번의 대여 사건을 의미한다.
```

### 현재 사실과 사건 당시 이력을 구분하는 기준

```text
현재의 최신 정보를 나타내는지, 사건이 발생한 당시의 값을 보존해야 하는지를 기준으로 구분한다.
```

# 6. Chapter 06에서 확정한 C-01~C-08 정책 해석

| ID | 확정 규칙 | 구현 방법 | 왜 필요한가 | Chapter 05에서는 왜 미확정이었나 |
| --- | --- | --- | --- | --- |
| C-01 | 이메일 문자열 중복 금지 | `UNIQUE` | 같은 이메일이 중복 저장되는 것을 방지하기 위해 | 이메일 중복을 허용할지 정책이 확정되지 않았기 때문 |

| C-06 | 존재하는 회원·도서만 참조 | `FOREIGN KEY` | 존재하지 않는 회원이나 도서의 대여 기록이 생기는 것을 막기 위해 | 테이블 간 참조 관계와 삭제 정책이 확정되지 않았기 때문 |
| C-07 | 대여 이력이 있는 부모 삭제 금지 | `ON DELETE RESTRICT` | 대여 기록이 참조하는 회원이나 도서를 삭제해 관계가 깨지는 것을 방지하기 위해 | 참조 중인 데이터를 삭제할 때 어떻게 처리할지 확정되지 않았기 때문 |
| C-08 | 도서당 미반납 대여 최대 한 건 | 부분 고유 인덱스 | 같은 도서가 동시에 여러 사람에게 대여 중인 상태가 되는 것을 막기 위해 | 미반납 상태의 중복 대여를 어떻게 처리할지 정책이 확정되지 않았기 때문 |

실행 파일:

> **중요:** 오류 테스트는 한 번에 하나씩 실행하고, 각 테스트가 끝난 뒤 기준 데이터가 유지되는지 확인합니다.

## 8-1. 허용되어야 하는 경계값

최소 3개를 실행·관찰합니다.

| 테스트 | 예상 | 실제 | 왜 허용되어야 하는가 |
| --- | --- | --- | --- |
| `due_at = borrowed_at` | 성공 | 성공 | 대여일과 반납 예정일이 같은 것은 `due_at >= borrowed_at` 조건을 만족하기 때문이다. |
| `returned_at = borrowed_at` | 성공 | 성공 | 대여한 당일 반납하는 것은 `returned_at >= borrowed_at` 조건을 만족하기 때문이다. |
| `returned_at = NULL` | 성공 | 성공 | 아직 반납하지 않은 대여는 `NULL`로 표현하도록 허용했기 때문이다. |
| `published_year = NULL` | 성공 | 성공 | 출판 연도는 필수값으로 정하지 않았기 때문에 `NULL`을 허용한다. |
| 공백이 아닌 한 글자 이름 | 성공 | 성공 | 이름은 공백만 아니면 허용되므로 한 글자 이름도 정상적인 값이다. |

## 8-2. 실패해야 하는 오류값

최소 6개를 실행합니다.

| 오류 테스트 | 기대 규칙 | 실제 결과 | 오류 메시지 핵심 | 실패해야 하는 이유 |
| --- | --- | --- | --- | --- |
| 필수값 NULL | `NOT NULL` | 실패 | `violates not-null constraint` | 필수 정보인 이름에는 NULL을 저장할 수 없기 때문이다. |
| ISBN NULL | `NOT NULL` | 실패 | `violates not-null constraint` | ISBN은 필수값으로 정했기 때문이다. |
| 이메일 중복 | `UNIQUE` | 실패 | `uq_members_nf_email` | 같은 이메일이 중복 저장되는 것을 막아야 하기 때문이다. |
| ISBN 중복 | `UNIQUE` | 실패 | `uq_books_nf_isbn` | 같은 ISBN의 도서가 중복 등록되는 것을 막아야 하기 때문이다. |
| 공백 이름/제목 | `CHECK` | 실패 | `chk_members_nf_name_not_blank` 또는 `chk_books_nf_title_not_blank` | 공백만 있는 이름이나 제목은 유효한 값으로 볼 수 없기 때문이다. |
| 존재하지 않는 회원 | `FOREIGN KEY` | 실패 | `fk_loans_nf_member` | 존재하지 않는 회원의 대여 기록이 생기면 안 되기 때문이다. |
| 존재하지 않는 도서 | `FOREIGN KEY` | 실패 | `fk_loans_nf_book` | 존재하지 않는 도서를 대여 기록에서 참조하면 안 되기 때문이다. |
| 날짜 순서 위반 | `CHECK` | 실패 | `chk_loans_nf_due_date` 또는 `chk_loans_nf_returned_date` | 반납 예정일이나 실제 반납일이 대여일보다 이전이면 안 되기 때문이다. |
| 두 번째 미반납 대여 | 부분 고유 인덱스 | 실패 | `uq_loans_nf_active_book` | 같은 도서에 동시에 두 개 이상의 미반납 대여가 존재하면 안 되기 때문이다. |
| 참조 중 부모 삭제 | `RESTRICT/FK` | 실패 | `fk_loans_nf_member` | 대여 기록이 참조 중인 회원을 삭제하면 데이터 관계가 깨지기 때문이다. |

# 9. 정규화와 무결성 제약조건 역할 비교

| 질문 | 나의 설명 |
| --- | --- |
| 정규화가 해결하는 문제 | 회원, 도서처럼 반복되는 정보를 분리하여 데이터 중복과 삽입·수정·삭제 이상을 줄인다. |
| `NOT NULL`이 해결하는 문제 | 반드시 필요한 값이 NULL로 저장되는 것을 막는다. |
| `UNIQUE`가 해결하는 문제 | 이메일이나 ISBN처럼 중복되면 안 되는 값의 중복 저장을 막는다. |
| `CHECK`가 해결하는 문제 | 공백 이름·제목이나 잘못된 날짜처럼 정해진 조건에 맞지 않는 값의 저장을 막는다. |
| `FOREIGN KEY`가 해결하는 문제 | 존재하지 않는 회원이나 도서를 참조하는 대여 기록이 생기는 것을 막는다. |
| 부분 고유 인덱스가 해결하는 문제 | 미반납 상태인 같은 도서의 대여가 동시에 두 건 이상 존재하는 것을 막는다. |

### 정규화만 잘하면 잘못된 데이터가 모두 차단되나요?

```text
아니다. 정규화는 데이터의 중복을 줄이고 각 사실을 적절한 테이블로 분리하는 역할을 하지만,
NULL, 중복 이메일, 잘못된 날짜, 존재하지 않는 회원 참조 같은 잘못된 값까지 모두 막아주지는 않는다.
따라서 정규화와 함께 무결성 제약조건을 적용해야 한다.
```

### 제약조건만 많이 넣으면 나쁜 구조가 좋은 구조가 되나요?

```text
아니다. 제약조건은 잘못된 값이나 관계를 차단하는 역할을 하지만,
한 테이블에 회원·도서·대여 정보가 반복해서 저장되는 구조 자체를 해결하지는 못한다.
따라서 먼저 정규화를 통해 데이터 구조를 적절히 분리하고,
확정된 업무 규칙에 맞는 제약조건을 함께 적용해야 한다.
```
